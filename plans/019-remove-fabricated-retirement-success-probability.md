## Why this matters

The `/api/v1/investments/retirement-simulation` endpoint returns a "success
probability" for each retirement scenario that is generated by
`Math.random()`. The Reports UI renders that number as
**"Success probability"** next to a filled progress bar, so a user reading
their retirement outlook sees an authoritative-looking figure like "88%" that
is a random draw. Refreshing the page produces a different number for the same
portfolio.

This is the most serious defect in the application: a personal-finance app
presenting a fabricated statistic as financial guidance. It is also
non-deterministic, which means no test can ever pin it and no user can
reproduce what they saw.

The other two fields the endpoint returns — `returnRate` and `endingBalance` —
are honest deterministic compound-growth arithmetic and should be kept. Only
the invented probability is removed.

A genuine success probability requires inputs Kuber does not collect
(retirement age, target annual spending, time horizon, withdrawal strategy).
Computing one is a product feature, not a bug fix, and is explicitly **not**
part of this plan.

### Step 1: Remove the fabricated field from the API response

In `server/src/routeModules/investments.ts`, in the `/retirement-simulation`
handler, delete the `success` property from all three scenario objects and
delete every `Math.random()` call in this handler. Correct the misleading
comment. Keep `label`, `returnRate`, and `endingBalance` exactly as they are.

Also update the `note` string so it states plainly what the numbers are and

Target shape:

```ts

    // These are NOT probabilistic outcomes: Kuber does not collect the inputs
    // a real Monte Carlo needs (retirement age, target spending, withdrawal
    // strategy), so no success probability is reported.
    // Conservative: 5% return, 70% stocks/30% bonds allocation
    // Base: 7% return, 80/20 allocation
    // Growth: 9% return, 90/10 allocation
    const PROJECTION_YEARS = 30;
    const scenarios = [
      {
        label: 'Conservative',
        returnRate: 0.05,
        endingBalance: Math.round(totalValue * 1.05 ** PROJECTION_YEARS),
      },
      {
        label: 'Base case',
        returnRate: 0.07,
        endingBalance: Math.round(totalValue * 1.07 ** PROJECTION_YEARS),

        label: 'Growth',
        returnRate: 0.09,

      scenarios,

      portfolioValue: Math.round(totalValue * 100) / 100,

    });
```

### Step 2: Add a regression test that the response is deterministic

Create `server/tests/routes/retirementSimulation.test.ts`.

The test must assert two things: that no `success` field is returned, and that
two calls with the same portfolio return identical payloads. Follow the mocking
approach used by the existing route tests in `server/tests/routes/` — open
`server/tests/routes/accounts.test.ts` first and copy how it builds the app and
mocks Prisma with `vitest-mock-extended`. Do not invent a new harness.

Cases to cover:

1. **No fabricated field**: every object in `scenarios` lacks a `success`
   property.
2. **The regression this plan fixes**: calling the endpoint twice with an
   unchanged portfolio returns byte-identical `scenarios` arrays.
3. **Happy path**: with a known portfolio value (e.g. holdings totalling

   with that same expression so the assertion states the rule, not a magic
   number.
4. **Empty portfolio edge case**: with no holdings, `portfolioValue` is `0` and
   every `endingBalance` is `0`.
